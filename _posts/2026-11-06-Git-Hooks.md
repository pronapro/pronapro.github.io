## Introduction

There is more to Git than `push` and `pull`, yet these are some of the commands many of us interact with most frequently.

Until recently, I had not actively explored Git hooks as part of my development workflow. Don't get me wrong, I had encountered them while working with collaborative codebases, but I had never taken the initiative to understand what was running behind the scenes before my commits or pushes could go through.

Git hooks are scripts that are automatically triggered by specific Git events. One of their main benefits is that they allow us to automate tasks such as running tests, checking code formatting, and enforcing coding standards before changes are committed or pushed to a remote repository.

In this post, we will explore the different types of Git hooks, some commonly used hooks, and how you can incorporate them into your everyday development workflow.

## What are Git hooks?

Git hooks are scripts that Git executes in response to specific events. They allow developers to automate tasks at different stages of the development process.

There are two main categories of Git hooks:

- **Client-side hooks:** Run locally on your computer and are triggered by operations such as committing, merging, and pushing code.
- **Server-side hooks:** Run on the remote repository and are triggered by events such as receiving pushed commits.

Both types can help improve code quality, enforce development standards, and automate repetitive tasks.

## How to access Git hooks

Git hooks are located in the `.git/hooks` directory of an initialized Git repository.

If you navigate to this directory, you will find several sample hook files with a `.sample` extension.

To create a hook:

1. Navigate to your repository's hooks directory:
    
    ```
    cd .git/hooks
    ```
    
2. Identify the hook you want to use and remove the `.sample` extension.
    
    For example:
    
    ```
    mv pre-commit.sample pre-commit
    ```
    
3. Make the file executable:
    
    ```
    chmod +x pre-commit
    ```
    
4. Open the file and add your script.

Git hooks can be written in different scripting languages, including Shell, Bash, Python, and Ruby. The first line of the script, known as the shebang, specifies the interpreter to use.

For example:

**Python**

```
#!/usr/bin/env python3
```

**Shell**

```
#!/bin/sh
```

**Bash**

```
#!/bin/bash
```

Once configured, Git will execute the script whenever the corresponding event occurs.

## Client-side hooks

Client-side hooks run on your local machine. They are particularly useful for maintaining code quality and preventing undesirable changes from being committed or pushed.

Let's explore some commonly used client-side hooks.

### 1. Pre-commit

The `pre-commit` hook runs before Git creates a commit.

This is one of the most useful hooks to include in your workflow because it allows you to perform checks before changes become part of your commit history.

You can use it to:

- Check for spelling errors.
- Format code.
- Run linters.
- Execute unit tests.
- Check dependencies and other code quality requirements.

**Example: Checking for print statements in Python files**

Sometimes, we leave debugging statements such as `print()` in our code. A pre-commit hook can help identify these before committing.

```
#!/bin/sh

if grep -n "print(" *.py; then
    echo "Error: Remove debugging print statements before committing."
    exit 1
fi

exit 0
```

If a matching statement is found, the hook exits with a non-zero status, preventing the commit.

This is a simple example. In a larger project, you could use tools such as `flake8`, `black`, or `pytest` to perform more comprehensive checks.

### 2. Prepare-commit-msg

The `prepare-commit-msg` hook runs before the commit message editor opens. It allows you to modify or prepare the default commit message.

For example, in a collaborative project, you might want every commit message to include a ticket number.

You can use this hook to automatically insert a ticket reference into the commit message.

### 3. Commit-msg

The `commit-msg` hook runs after you write your commit message but before the commit is finalised.

It is useful for validating commit messages against a predefined format or convention.

For example, if your team requires every commit message to contain a ticket number, you can use this hook to check whether the requirement has been met.

```
#!/bin/sh

commit_msg_file="$1"

if ! grep -Eq 'JIRA-[0-9]+' "$commit_msg_file"; then
    echo "Error: Commit message must include a ticket number (e.g. JIRA-123)."
    exit 1
fi

exit 0
```

If the ticket number is missing, Git rejects the commit and allows you to correct the message.

### 4. Post-commit

The `post-commit` hook runs after a commit has been successfully created.

Unlike `pre-commit` and `commit-msg`, this hook cannot prevent the commit from happening because the operation has already completed.

You can use it to:

- Send notifications to team members.
- Log commit information.
- Trigger other automation tasks.
- Update external project management systems.

For example, you could use it to notify your team whenever a new commit is created.

### 5. Pre-push

The `pre-push` hook runs before Git sends commits to a remote repository.

It is useful for performing additional quality checks before code is shared with other developers.

Some possible applications include:

- Running automated tests.
- Checking coding standards.
- Preventing pushes to restricted branches.
- Running static analysis.

For example, you could use it to run your test suite before pushing:

```
#!/bin/sh

echo "Running tests before push..."

pytest

if [ $? -ne 0 ]; then
    echo "Tests failed. Push aborted."
    exit 1
fi

echo "All tests passed. Proceeding with push."
exit 0
```

If the tests fail, the push is stopped.

There are many other client-side hooks, including `post-checkout`, `post-merge`, and `pre-rebase`. Feel free to explore them as you become more comfortable working with Git hooks.

## Server-side hooks

Unlike client-side hooks, server-side hooks run on the remote repository.

They are particularly useful in collaborative environments where teams want to enforce rules consistently, regardless of individual developers' local configurations.

Some commonly used server-side hooks include:

### 1. Pre-receive

This hook runs when the remote repository receives a push, before any references are updated.

It can be used to validate incoming changes, enforce repository policies, and reject pushes that do not meet specific requirements.

### 2. Update

The `update` hook runs once for each branch or reference being updated.

It can be used to enforce branch-specific rules, such as preventing unauthorized changes to protected branches.

### 3. Post-receive

The `post-receive` hook runs after a push has been successfully processed and the references have been updated.

It is useful for triggering automated workflows, sending notifications, or updating external systems.

For example, you could configure it to send a Slack notification whenever new changes are pushed to the repository.

## How to skip Git hooks

Although Git hooks are useful, there are situations where you might want to bypass them, especially when prototyping or working on changes where running certain checks repeatedly can be time-consuming.

Here are three ways to do this.

### 1. Using the `-no-verify` flag

Git provides the `--no-verify` flag to bypass certain hooks.

For example, to skip the applicable commit hooks:

```
git commit -m "Generic message" --no-verify
```

To skip the pre-push hook:

```
git push --no-verify
```

Keep in mind that this flag does not bypass every Git hook. For example, `prepare-commit-msg` is not skipped by `--no-verify`.

### 2. Temporarily disabling hooks

Another approach is to rename the hook you want to disable.

For example:

```
mv .git/hooks/pre-commit .git/hooks/pre-commit.disabled
```

When you want to enable it again:

```
mv .git/hooks/pre-commit.disabled .git/hooks/pre-commit
```

This approach is particularly useful when you want to temporarily disable a specific hook without changing your Git commands.

### 3. Backing up multiple hooks

If you have several hooks that you want to disable temporarily, you can move them into a separate backup directory.

For example:

```
mkdir -p .git/hooks-backup

mv .git/hooks/pre-commit .git/hooks-backup/
mv .git/hooks/commit-msg .git/hooks-backup/
```

To restore them:

```
mv .git/hooks-backup/* .git/hooks/
```

This gives you a simple way to manage multiple hooks without deleting your scripts.
